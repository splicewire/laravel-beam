# Particle operations

`beam.particle.operations` holds every **named operation**: an action on a resource that isn't one of
the five CRUD verbs, such as `tickets.close`, `songs.share` or `invoices.export`. Each entry is a
`ParticleOperation` saying what the operation accepts, what it returns, which ability it needs and how
it runs. Beam's generic operation controller looks the operation up here and runs it, so you write the
handler and never a controller.

## Keys

An operation's key is `<resource>.<name>`, under the registry's root: closing a ticket lives at
`beam.particle.operations.tickets.close`. Because the resource is its own key segment, you can ask
"what can I do to a ticket?" by listing everything under `beam.particle.operations.tickets`. The
operation computes its own key from its declaration, so you never assemble one by hand.

## Declaring an operation

Put `#[ParticleOp]` on a small class that holds the handler, and let discovery register it:

```bash
php artisan splicewire:beam:make:particle-op
```

The generator writes the attribute with all three shape slots explicit (input, output and ability)
plus the class's `handle()` method. Mount the resource's operations in your route file:

```php
Particle::ops('tickets', 'tickets', [CloseTicket::class]);
```

Each operation mounts once, at `tickets/{id}/close` for the common record-scoped case, named
`tickets.close`.

## Graph operations: a resource whose records form a graph

Some operations are not declared at all. When a resource's records form a graph, such as a tree by a
parent column or rows joined by an edge table, Beam registers four read operations for it:

| operation | address | answers |
|---|---|---|
| `graph` | `GET {uri}/graph` | a bounded slice, optionally from `roots[]` |
| `graph.cycles` | `GET {uri}/graph/cycles` | at most `limit` cycles |
| `graph.neighbours` | `GET {uri}/{id}/graph/neighbours` | the record's neighbourhood, by `direction`, `depth` and `limit` |
| `graph.path` | `GET {uri}/{id}/graph/path?target={id}` | the shortest path from the record to `target` |

The query parameters have no defaults. `graph` requires `depth` (at least 0) and `limit` (at least 1), with
`roots[]` optional. `graph.neighbours` requires `direction` (`descendants`, `ancestors` or `both`), `depth`
(at least 0) and `limit` (at least 1). `graph.cycles` requires `limit` (at least 0), and `graph.path`
requires `target`. A missing or out-of-range parameter is a 422.

The four share one read gate, and it **fails closed**. Each runs the resource's read gate through
`ResourceReadGuard::inspectRead()`, not the list's Public Read floor. A guest who may list the resource
through a declared Public Read is still refused with a 403 by all four, because a graph exposes how
records connect, which the Public Read never narrowed.

A resource gets them in one of two ways. A backing that implements `GraphsRecords` hands Beam a graph
over its own records. Or a resource backed by **one Eloquent model** declares where its edges are in
one `graph:` slot, and Beam supplies the graph itself, with no backing class to write. The slot takes
`new ParentEdge('parent_id', label: 'name')` for a self-referencing column, or `new EdgeTable(…)` for an
edge table. It needs `splicewire/laravel-beam` at `78caf162` or later, and it is refused at registration
on any backing that is not one plain model.

This is how `splicewire/laravel-beam-taxonomy` declares `silos` (`label: 'name'` labels each node with
the silo's name, or its id where that is empty):

{/* excerpt: splicewire/laravel-beam-taxonomy@a1867c8c4a4db517913cc442fd028525d4ec5001 · src/BeamTaxonomyServiceProvider.php:164-178 */}

```php
            $registry->register(new ParticleResource(
                key: 'silos',
                backing: $siloModel,
                data: config('beam.taxonomy.data.silo'),
                input: config('beam.taxonomy.input.silo'),
                includes: ['fragments'],
                // The declared row scope (integrator ruling c353ac01): the cascade narrowing SiloQuery's base applies.
                scope: fn (EloquentBuilder $query): EloquentBuilder => SiloQuery::rowScope($query),
                label: 'Silos',
                group: 'Taxonomy',
                // graph-operations 05 (D7): silos is the first consumer. The `parent_id` tree declares its
                // edges in one slot; beam derives the four graph read operations over the same row-scoped
                // query. `label: 'name'` labels nodes from the silo name (04 label ruling), id where null.
                graph: new ParentEdge('parent_id', label: 'name'),
            ));
```

**above** the `Route::beamUxSite(...)` page catch-all, because the catch-all's `{path}` answers every
address declared after it. This is the change that adopted `silos` on the proof host, a fresh
`laravel-beam-starter` install:

With the `graph:` slot, the graph is built from the resource's own list query, with its row scope applied.
A `GraphsRecords` backing scopes its own graph to the reader, from the same filters its list takes.
Either way, **a record the reader cannot list is not a node** and no path runs through it. Asking from such a record is a 404, while
asking for a path TO one gives an empty path. `graph.path` is directed: it walks from the source record
`{id}` downward, along the edges, to `?target=`. In a tree that means from an ancestor to its descendant,
so the reverse request is an empty path, not an error. Depth and node count are capped by
`beam.core.graph` (`max_depth`, `max_nodes`). A request past a cap, or a scoped set too large to load,
is refused with a 422 naming the limit. It is never quietly truncated.

**A node is a reference, never row data:** `{ id, type, resource, label }`, and an edge is
`{ from, to, type, weight }`. Read a record's fields through the resource itself.

## Overriding an operation

The [**duplicate-key policy**](/beam/docs/foundations/registries#key-policies) is
**supersede**, and it is how you replace an operation a package ships: register your own declaration
under the same `<resource>.<name>` from a provider that boots later. Yours runs, and the package's
original stays readable as a superseded entry, so the override can be audited rather than guessed
from boot order.

# Particle resources

`beam.particle.resources` holds every **particle resource** in your application: one entry per
resource key (`songs`, `tickets`, `tenants`), each a `ParticleResource` declaration saying what the
rows are, how they are projected onto the wire and what a write accepts. Beam's generic REST
controller reads a declaration from here on every request, and
[Frame](/beam/docs/laravel/frame) reads the same entry to draw its list, form and detail screens. One
registration serves both.

## Where entries come from

You rarely call this registry yourself. Declare the resource on a data class with
`#[ParticleResource]`, and Beam's boot-time discovery registers it for you:

```bash
php artisan splicewire:beam:make:particle-resource
```

The generator writes the attribute with its backing, read projection and write shape spelled out, plus
the mount line for your route file.

Three optional flags:
- `--filters` emits a `*FilterData` class from the model's actual table columns, and prints the one discovery line
  it needs.
- `--cascade-policy` prints the model's `#[UseCascadePolicy]` lines; it never edits an authored model.
- `--section=` declares `section:`, and warns, printing a registration line, when no `NavSection` seats it. If a
  hand-authored navigation can't be read from the console, it says whether the section is seated is unknown.

Discovery finds the class when it is listed in
`beam.core.particle.classes` or sits under a path in `beam.core.particle.discover_paths`. Beam's own
resources are always scanned, and every installed Beam package registers its own the same way.

You can also register from a service provider. That is how a package contributes a resource without an
attribute scan:

```php
use Splicewire\Beam\Particle\ParticleResource;
use Splicewire\Beam\Particle\ParticleResourceRegistry;

public function boot(): void
{
    $this->app->make(ParticleResourceRegistry::class)->register(
        new ParticleResource(key: 'songs', backing: Song::class),
        by: 'acme/music',
    );
}
```

Pass `by:` with your package name. Beam records it, and the registrant panel on this page reads it back.

## One entry, read three ways

This example registers a read-only resource over rows a package holds in memory, with no model
behind it. It then reads the entry back three ways: the registry's keys (Beam's own resources
first, then the new one), the row `splicewire:beam:particle:resources` reports for it, and the
`ResourceDefinition` that Frame draws its list and detail screens from. The report's capability
columns (`streams`, `resolves`, `writes`) come from what the backing implements, while
`creatable`, `editable` and `deletable` come from the declaration. The JSON is the real output of
the PHP beside it, captured by the package and re-checked by its test suite.

## Replacing a resource you don't own

The [**duplicate-key policy**](/beam/docs/foundations/registries#key-policies) is
**supersede**, and that is deliberate: it is the override seam. If a package ships `tickets` and
your application registers its own `tickets` declaration from a provider that boots later, yours
wins, in the same position, and the displaced one stays readable as a superseded entry. A scan that
runs twice registers the same declaration twice and nothing changes.

<Callout type="warning" title="An override can't loosen reads">

Two things cannot change on an override: a resource's read policy and its read boundary. Registration
refuses a declaration that would swap either. Those are authorization decisions, and an override is not
allowed to loosen them silently.

</Callout>

## Realms

A resource can say which [realms](/beam/docs/foundations/realms-and-surfaces) it belongs to when it
registers (`operator`, `tenant`, …). Realm membership is recorded beside the entry, not as a second key:
one resource, many realms, no duplicate. A resource that names no realm falls back to the host's
`frame.realms` map.

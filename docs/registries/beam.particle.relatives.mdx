# Particle relatives

`beam.particle.relatives` holds **relative edges**: declarations that mount one particle resource
underneath another, so `media` can be listed as `/fragments/{fragment}/media` as well as on its own. Each
entry is a `ParticleRelative` naming the child resource, the parent resource, the parent model the URL
segment binds to, and how the child hangs off the parent: a relation name like `media`, or a scope.

## Keys

An edge is keyed `<parent>.<child>`, so `fragments.media` lives at
`beam.particle.relatives.fragments.media`. Listing everything under
`beam.particle.relatives.fragments` gives you every resource mounted beneath fragments.

## Who declares an edge

An edge belongs to whoever owns the *coupling*, which is usually neither resource's package. The
package that ships `media` is generic and shouldn't know fragments exist; the package that ships
fragments shouldn't depend on a media package. Your application, which installs both, is the one that
knows they belong together, so it declares the edge in a class of its own:

```bash
php artisan splicewire:beam:make:particle-relative
```

```php
#[ParticleRelative(child: 'media', of: 'fragments', model: Fragment::class, via: 'media')]
class FragmentMediaRelative {}
```

Then mount every edge declared against a parent with one line in your route file:

```php
Particle::relatives('fragments');
```

For an edge that is a scope rather than a named relation, leave out `via:` and give the class a
`public static function via(Model $parent, Builder $query): Builder`. Keeping it on the class rather
than in a closure is what lets `route:cache` serialize the route table.

## Duplicates

The policy is **supersede**: a second declaration of the same `<parent>.<child>` pair replaces the
first, and the first stays readable as superseded. Two different edges between the same two
resources can't be expressed, because the key is only the two ends.

# Seed steps

`beam.seed.steps` is the list of seeders `splicewire:beam:seed` runs. Every Beam package that ships
seed data registers its seeder here from its own service provider, so a host's `DatabaseSeeder`
calls one command instead of naming each package's seeder by class. Each entry is a `SeedStep`,
filed under the package's Composer name. It names the seeder class, an order, the memberships a
[Seeding Scenario](beam.seed.scenarios) selects it by, and an optional config gate.

## Registering your seeder

From your provider's `boot()`:

```php
use Splicewire\Beam\Seed\BeamSeedManifest;

$this->app->make(BeamSeedManifest::class)->register(
    package: 'splicewire/laravel-beam-tenancy',
    seederClass: DemoTenantSeeder::class,
    order: 20,
    memberships: SeedStep::DEMO,
);
```

Each seeder runs through `db:seed --class`. Steps run in ascending `order` (default `100`), and
steps with the same order run in registration order. That lets the foundational rows exist before
the data that builds on them: [Splicewire](https://splicewire.com/) seeds its system account at
`10`, before tenancy's demo tenant at `20`.

## Memberships

`memberships` says what kind of data the step writes. Leave it out and the step is a `baseline`
step, which every [Seeding Scenario](beam.seed.scenarios) runs. A step that fabricates demo subjects
(users, teams, a tenant) says `SeedStep::DEMO`, and runs only under a scenario that includes `demo`:
`local`, out of the box. A step never reads the environment itself. Which environment gets demo data
is the scenario's decision, and a host changes it in `config/beam/seed.php`.

The command reports a step the scenario leaves out as **left out by scenario**, apart from a gated
skip.

## Config gates

`configGate` names a config key that must be truthy for the step to run. Leave it out and the step
always runs. Use a gate for "this step cannot run here", such as an estate this host declared
absent. Don't use it to choose which environment gets demo data; a membership does that. The command
reports a gated step as **skipped**, with the key that was off, so "nothing registered" and
"registered but switched off" are distinguishable in its output.
A seeder that throws or exits non-zero is a failure, not a skip. The rest of the steps still
run, the data they seeded stays, and the command exits non-zero unless you pass
`--tolerate-failures`. To keep a seeder from running, use its gate.

## What a duplicate means here

The [**duplicate-key policy**](/beam/docs/foundations/registries#key-policies) is
**supersede**, keyed by package name. Registering again replaces your earlier step, so a provider
that boots twice never seeds twice.
